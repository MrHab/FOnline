# Архитектура

Production-приложение — один Node.js-процесс из `server.js`, который обслуживает
REST API, Socket.IO и, при локальном запуске, статический клиент. В production
статику рекомендуется отдавать напрямую через Nginx.

## Слои

| Слой | Основные файлы | Ответственность |
|---|---|---|
| HTTP и realtime | `server.js` | auth, персонажи, комнаты, игровой мир, Socket.IO |
| Серверные подсистемы | `src/server/*.js` | живая пустошь, маршруты, collider-геометрия, NPC-инвентарь |
| Клиентский shell | `public/index.html`, `public/js/game.js` | DOM, vendor-скрипты, загрузка игрового кода |
| Игровой клиент | `public/js/game/*.js` | Three.js, UI, input, отображение server state |
| Стили | `public/css/game.css`, `public/css/game/*.css` | desktop/mobile HUD и окна |
| Авторские данные | `data/*.json`, `data/locations/*.json` | карта, локации, квесты, встречи, экономика |
| Runtime-данные | `DATA_DIR/*.json` | аккаунты, персонажи, состояние симуляции |
| Инструменты | `tools/*.js` | генераторы, редакторы и проверки |

`src/server/authoritative-server.js` не импортируется production-сервером. Это
исторический reference-файл, который пока читают несколько проверок; менять
runtime-поведение нужно в `server.js`.

## Запуск клиента

1. `public/index.html` загружает локальные Three.js, GLTFLoader и Socket.IO.
2. `public/js/game.js` параллельно получает collider-каталог и все файлы из
   `GAME_SCRIPT_PARTS`.
3. После завершения запросов части объединяются в объявленном порядке и
   выполняются как один script scope.
4. Bootstrap определяет устройство, поднимает auth UI, выбирает персонажа и
   только затем выполняет Socket.IO `join`.
5. Серверный `join` возвращает состояние персонажа, комнаты и
   `characterLeaseId`; клиент строит сцену под экраном загрузки.

Параллельная загрузка не означает независимые ES-модули: порядок частей и общая
лексическая область остаются частью контракта.

## HTTP-контур

REST используется для:

- регистрации, входа, heartbeat, выхода и восстановления пароля;
- списка, чтения, синхронизации и удаления персонажей;
- получения локаций, квестов, глобальной карты и публичного состояния пустоши;
- локальных dev-редакторов мира, защищённых loopback-доступом или
  `DEV_ADMIN_TOKEN`;
- `/health`.

Bearer token привязан к `deviceId`. Для чтения и записи активного персонажа
клиент также передаёт `clientInstanceId` и выданный сокетом
`characterLeaseId`.

## Realtime-контур

Socket.IO обслуживает движение, действия и общие сущности комнаты:

1. `join` проверяет account session и блокировку персонажа.
2. `input` задаёт направление, а серверный тик интегрирует движение и проверяет
   коллизии.
3. `state` передаёт movement proposal и профильные изменения; сервер
   нормализует и при необходимости отправляет `authoritativePlayerState`.
4. Частый volatile `playerState` передаёт движение другим клиентам.
5. Полный `snapshot` периодически сверяет состав и статус игроков комнаты.
6. Действия с боем, лутом, торговлей и миром подтверждаются ack-ответом, после
   чего сервер рассылает изменившееся общее состояние.

Поздний пакет из старой комнаты отбрасывается по `roomId`, `locationId`,
времени/sequence. Отсутствие сущности в полном серверном snapshot означает, что
клиент должен удалить её визуал.

## Серверная авторитетность

Сервер хранит и проверяет:

- координаты, комнату, HP/AP, прогрессию и экипировку игроков;
- серверный инвентарь, вес, быстрые предметы и состояние оружия;
- NPC, их снаряжение, боеприпасы, AI, трупы и лут;
- предметы на земле, ресурсы, контейнеры, торговые запасы и хранилища;
- глобальные маршруты, встречи, отряды, задания и фракционные изменения;
- допустимость дистанции, LOS, коллизий и переходов.

Клиент отвечает за input, path preview, анимацию, интерфейс, fog-визуализацию и
краткую визуальную предикцию. Подробности:
[авторитетные правила](SERVER_AUTHORITATIVE_RULES.md).

## Два масштаба мира

Локальная комната — физическая 3D-локация с игроками, NPC и объектами.
Глобальная пустошь — отдельная серверная симуляция поселений, ресурсов,
инфраструктуры, караванов и конфликтов. Сервер связывает уровни через
`globalTravel*`, `serverWorldTransfer`, world zones и уникальные экземпляры
точек.

Симуляция может жить без открытой 3D-комнаты. Пустые обычные комнаты не должны
постоянно выполнять полный локальный AI; исключения — короткое settle-окно,
активный realtime-бой и ожидающий выхода onsite-отряд.

## Данные и запись

- Авторские JSON загружаются из репозитория даже при внешнем `DATA_DIR`, если
  runtime-копии отсутствуют.
- `users.json`, `saves.json` и `wasteland-sim.json` записываются атомарно.
- Нечитаемые runtime JSON копируются как `*.corrupt-*` перед использованием
  fallback-структуры.
- Генерируемые GLB и `model-colliders.json` обновляются только соответствующими
  инструментами.

## Проверки

```bash
npm run check:server
npm run check:client
npm run check:data
npm run smoke
npm run check
```

Smoke-проверка запускает изолированный сервер на временном порту и временном
`DATA_DIR`, проверяет REST, статику, Socket.IO и жизненный цикл нескольких
персонажей без доступа к production-данным.
