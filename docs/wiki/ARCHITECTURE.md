# Архитектура

Production-приложение — один Node.js-процесс из `server.js`, который обслуживает
REST API, Socket.IO и, при локальном запуске, статический клиент. В production
статику рекомендуется отдавать напрямую через Nginx.

## Слои

| Слой | Основные файлы | Ответственность |
|---|---|---|
| HTTP и realtime | `server.js` | auth, персонажи, комнаты, игровой мир, Socket.IO |
| Серверные подсистемы | `src/server/*.js` | живая пустошь, маршруты, collider-геометрия, NPC-инвентарь |
| Клиентский shell | `public/index.html`, `public/js/game.js` | DOM, vendor-скрипты, загрузка игрового кода |
| Игровой клиент | `public/js/game/*.js` | Three.js, UI, input, отображение server state |
| Стили | `public/css/game.css`, `public/css/game/*.css` | desktop/mobile HUD и окна |
| Авторские данные | `data/*.json`, `data/locations/*.json` | карта, локации, квесты, встречи, экономика |
| Runtime-данные | `DATA_DIR/*.json` | аккаунты, персонажи, состояние симуляции |
| Инструменты | `tools/*.js` | генераторы, редакторы и проверки |

Единственный серверный entry point — `server.js`. Модули `src/server/*.js`
активны только когда явно импортированы из него; отдельной копии сервера в
`src/server/` больше нет.

## Запуск клиента

1. `public/index.html` загружает локальные Three.js, GLTFLoader и Socket.IO.
2. `public/js/game.js` параллельно получает collider-каталог и все файлы из
   `GAME_SCRIPT_PARTS`.
3. После завершения запросов части объединяются в объявленном порядке и
   выполняются как один script scope.
4. Bootstrap определяет устройство, поднимает auth UI и загружает выбранного
   персонажа. Выбор single-flight: пока один запрос выполняется, новый клик не
   начинает вторую загрузку, а смена token/эпохи инвалидирует старый ответ.
5. Затем клиент выполняет единственный Socket.IO `join` для текущего поколения
   соединения. Повторный вызов во время входа присоединяется к уже созданному
   promise, а успешный повтор на том же socket считается идемпотентным.
6. Серверный `join` возвращает состояние персонажа, комнаты и
   `characterLeaseId`; клиент строит сцену под экраном загрузки.

Параллельная загрузка не означает независимые ES-модули: порядок частей и общая
лексическая область остаются частью контракта.

После появления auth token клиент работает в одном из трёх явных режимов
авторитетности: `server`, `offline-local` или `blocked`. `server` разрешён только
при живом присоединённом socket; `offline-local` — только в действительно
локальной игре без token. Во время входа, reconnect и после разрыва
авторизованная игра переходит в `blocked`, очищает удерживаемый ввод и старые
сетевые сущности и не включает локальную симуляцию как запасной источник истины.
Требование online-сервера закрепляется за уже открытым серверным персонажем:
очистка token после актуального ответа `401` оставляет его мир в `blocked`.
Лишь мир, который изначально не имеет token, server-character и online-
привязки, может использовать `offline-local`; штатный logout сначала закрывает
online-мир и затем снимает это требование.

## HTTP-контур

REST используется для:

- регистрации, входа, heartbeat, выхода и восстановления пароля;
- списка, чтения, синхронизации и удаления персонажей;
- получения локаций, квестов, глобальной карты и публичного состояния пустоши;
- локальных dev-редакторов мира, по умолчанию закрытых и доступных только через
  явно выбранный `DEV_API_MODE=local|token`;
- `/health`.

Bearer token привязан к `deviceId`. Для чтения и записи активного персонажа
клиент также передаёт `clientInstanceId` и выданный сокетом
`characterLeaseId`.

## Realtime-контур

Socket.IO обслуживает движение, действия и общие сущности комнаты:

1. Single-flight `join` проверяет account session и блокировку персонажа;
   повтор для того же аккаунта, персонажа и `clientInstanceId` на уже
   присоединённом socket возвращает текущее состояние без новой lease.
   На клиенте готовность дополнительно привязана к token, character,
   `clientInstanceId`, socket id и полученной lease. Join-waiter запоминает
   token/character/client-контекст, поэтому вход другого персонажа не может
   завершить старое ожидание.
2. `state` передаёт актуальный movement proposal и профильные изменения; сервер
   нормализует и при необходимости отправляет `authoritativePlayerState`.
   Совместимое legacy-событие `input` по-прежнему интегрируется серверным тиком,
   но без обновления более 1250 мс принудительно становится нейтральным.
3. Частый volatile `playerState` передаёт движение другим клиентам.
4. Полный `snapshot` периодически сверяет состав и статус игроков комнаты.
5. Действия с боем, лутом, торговлей и миром подтверждаются ack-ответом, после
   чего сервер рассылает изменившееся общее состояние.

Для боевых действий, перезарядки, добычи, лута трупов и контейнеров клиент
сохраняет контекст отправки ack: socket generation/id, `roomId`, join identity и
lease. Поздний callback после disconnect, смены комнаты, персонажа или lease
игнорируется. Переходы между комнатами используют отдельный контракт и не
помещаются в same-room guard.

Поздний пакет из старой комнаты отбрасывается по `roomId`, `locationId`,
времени/sequence. Отсутствие сущности в полном серверном snapshot означает, что
клиент должен удалить её визуал.

Обычный `ack.self` сверяет параметры, инвентарь и HUD, но не переставляет
локального игрока по `x/z`. Координаты применяются явно при `join` и переходе
между локациями либо по серверному состоянию с причиной
`movementCorrection`.

## Серверная авторитетность

Сервер хранит и проверяет:

- координаты, комнату, HP/AP, прогрессию и экипировку игроков;
- серверный инвентарь, вес, быстрые предметы и состояние оружия;
- NPC, их снаряжение, боеприпасы, AI, трупы и лут;
- предметы на земле, ресурсы, контейнеры, торговые запасы и хранилища;
- глобальные маршруты, встречи, отряды, задания и фракционные изменения;
- допустимость дистанции, LOS, коллизий и переходов.

Клиент отвечает за input, path preview, анимацию, интерфейс, fog-визуализацию и
краткую визуальную предикцию. Эти локальные системы выполняют игровой fallback
только в режиме `offline-local`; режим `blocked` замораживает игровые действия
до новой серверной сверки. Подробности:
[авторитетные правила](SERVER_AUTHORITATIVE_RULES.md).

## Два масштаба мира

Локальная комната — физическая 3D-локация с игроками, NPC и объектами.
Глобальная пустошь — отдельная серверная симуляция поселений, ресурсов,
инфраструктуры, караванов и конфликтов. Сервер связывает уровни через
`globalTravel*`, `serverWorldTransfer`, world zones и уникальные экземпляры
точек.

Симуляция может жить без открытой 3D-комнаты. Пустые обычные комнаты не должны
постоянно выполнять полный локальный AI; исключения — короткое settle-окно,
активный realtime-бой и ожидающий выхода onsite-отряд.

## Данные и запись

- Авторские JSON загружаются из репозитория даже при внешнем `DATA_DIR`, если
  runtime-копии отсутствуют.
- `users.json`, `saves.json` и `wasteland-sim.json` записываются атомарно.
- При старте членство игроков в отрядах из `wasteland-sim.json` сверяется с
  активными принятыми работами, account/character identity и фракциями
  персонажей из `saves.json`.
- Нечитаемые runtime JSON копируются как `*.corrupt-*` перед использованием
  fallback-структуры.
- Генерируемые GLB и `model-colliders.json` обновляются только соответствующими
  инструментами.

Клиент сериализует HTTP-сохранения через generation-aware single-flight очередь:
в сети одновременно находится не более одного save, а более новая генерация
записывается только после завершения предыдущей. Один drain выполняет не более
двух записей, поэтому непрерывные изменения оставляют свежую dirty-генерацию
следующему autosave-интервалу вместо бесконечного HTTP-цикла. Dirty-флаг
очищается лишь когда сохранена последняя запрошенная генерация. Проверки token, `characterId`,
`clientInstanceId` и lease не дают позднему ответу старого контекста отметить
нового персонажа сохранённым. Logout и переключение персонажа дожидаются
финального поколения и на это время замораживают ввод/игровые действия; если
запись не подтверждена, операция отменяется до disconnect и старый контекст
остаётся активным для повторной попытки.
Публикация результата в платформенный leaderboard запускается после успешной
серверной записи как detached best-effort задача: она повторно проверяет
контекст, но её задержка или ошибка не удерживает очередь и переходы.

## Проверки

```bash
npm run check:server
npm run check:client
npm run check:world-party
npm run check:data
npm run smoke
npm run check
```

Smoke-проверка запускает изолированный сервер на временном порту и временном
`DATA_DIR`, проверяет REST, статику, Socket.IO и жизненный цикл нескольких
персонажей без доступа к production-данным.
