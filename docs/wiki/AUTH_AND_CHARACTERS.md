# Аккаунты и персонажи

Аккаунт и персонаж — разные сущности. Аккаунт отвечает за вход и список
персонажей; каждый персонаж имеет собственное серверное состояние и отдельную
блокировку активной игровой сессии. Марки и синь лежат на счёте аккаунта
(`accounts` в `saves.json`) и общие для всех его персонажей; правила — в
[авторитетных правилах](SERVER_AUTHORITATIVE_RULES.md).

## Быстрый гостевой вход

Кнопка «Начать сразу» создаёт или восстанавливает гостевой профиль, привязанный
к случайному `deviceId` этого устройства: Unity-клиент хранит его в
`PlayerPrefs` (`roa.deviceId`) и передаёт заголовком `X-Device-Id`.
Логин гостевой учётной записи — `guest_` и первые 24 символа SHA-256 отпечатка
`deviceId` (`src/server/guest-auth.js`); без корректного `deviceId` сервер
отвечает `400`. Повторный быстрый вход на том же устройстве продолжает
последнего гостевого персонажа. Маршрут `POST /api/auth/guest` проходит через
тот же ограничитель частоты, что регистрация и обычный вход.

Новый гостевой персонаж «Странник» создаётся без экрана распределения по
быстрому старту `independentMercenary` каталога прогрессии: Мощь 5,
Наблюдательность 7, Стойкость 6, Влияние 5, Интеллект 5, Реакция 7 и Чутьё 5;
профили «Лёгкое оружие» и «Скрытность»; черты «Меткий глаз» и «Падальщик». После
запуска это обычный серверный персонаж: обучение, комнаты, бой, сохранения и
блокировка параллельной сессии работают без отдельных гостевых исключений.

Гостевой профиль нельзя восстановить после очистки локальных данных
устройства (`PlayerPrefs` или данных браузера в WebGL). Поэтому
интерфейс называет обычный логин постоянным аккаунтом и не обещает перенос
гостевого прогресса.

## Регистрация и вход

Регистрация через `POST /api/auth/register` проверяет:

- логин из 3–32 символов `a-z`, цифр и `._@-`;
- уникальный email длиной не более 254 символов;
- пароль длиной 8–128 символов.

Логин и email нормализуются в lower case. Пароль хранится как
PBKDF2-SHA512 hash: 120 000 итераций, случайная 16-byte salt, 64-byte
результат. Хеширование выполняется асинхронно в ограниченной очереди, поэтому
один вход не блокирует simulation tick и Socket.IO. По умолчанию одновременно
работают не более четырёх PBKDF2-задач, а вся очередь ограничена 64 запросами;
при переполнении auth endpoint отвечает `503` с `Retry-After`. Вход с
неизвестным логином проходит ту же PBKDF2-проверку на фиктивной записи, поэтому
время ответа не раскрывает наличие аккаунта.

Сессионный token создаётся через `crypto.randomBytes(32)`. Клиент также
передаёт сохранённый `deviceId`, но сам endpoint регистрации не отклоняет
пустое значение.

Auth-endpoints (гостевой вход, регистрация, вход, запрос и подтверждение
сброса пароля) ограничены двумя in-memory бюджетами на десять минут:

- 20 попыток на пару `IP + login/email` (для гостевого входа — `deviceId`);
- 60 попыток со всего IP, поэтому перебор случайных логинов не обходит защиту.

Отказ — `429` с `Retry-After`. Успешный запрос очищает только бюджет
конкретного login/email, сохраняя общий IP-бюджет. Таблица ограничена 10 000
записями и при заполнении fail-closed отклоняет новые попытки вместо
неограниченного роста памяти. Production Nginx передаёт реальный адрес в
`X-Forwarded-For`; сервер доверяет этому заголовку только если прямое
соединение пришло с loopback-прокси.

Настройки:

```text
AUTH_RATE_WINDOW_MS=600000
AUTH_RATE_MAX_ATTEMPTS=20
AUTH_RATE_IP_MAX_ATTEMPTS=60
AUTH_RATE_MAX_BUCKETS=10000
PASSWORD_HASH_CONCURRENCY=4
PASSWORD_HASH_MAX_PENDING=64
```

WebGL-сборка обращается к API того origin, с которого загружена страница. В
редакторе и Standalone адрес сервера задаёт поле `BaseUrl`
(`http://127.0.0.1:3000` по умолчанию) и строка сервера на экране входа.
Сторонние origin для REST и Socket.IO перечисляет переменная `ORIGINS`; без неё
разрешены loopback- и LAN-адреса самого сервера.

## HTTP-сессия

Клиент передаёт token как `Authorization: Bearer ...` или `X-Auth-Token`.
Дополнительные заголовки:

| Заголовок | Назначение |
|---|---|
| `X-Device-Id` | постоянный id устройства |
| `X-Client-Instance-Id` | id экземпляра клиента; Unity создаёт новый вместе с `RoaAuthClient` |
| `X-Character-Lease-Id` | lease активного персонажа, полученная через Socket.IO `join` |
| `X-Device-Type` | `desktop` или `mobile` |
| `X-Control-Type` | `keyboard_mouse`, `touch` или `gamepad` |

Token привязан к `deviceId`: запрос с другим `deviceId` получает `401`.
Один и тот же аккаунт нельзя одновременно открыть на разных устройствах
(`409`). После исчезновения живого socket блокировка неактивной сессии
действует до `SESSION_LOCK_MS` — по умолчанию 120 секунд. На том же `deviceId`
новый вход заменяет старые токены этого устройства.

`POST /api/auth/heartbeat` обновляет `lastSeenAt`; Unity шлёт его раз в
10 секунд, после неудачи — через 60. Частые heartbeat и `GET /api/auth/me`
объединяют запись `users.json` в окно до одной секунды; login, logout, reset и
Socket.IO join/disconnect сбрасывают ожидающую запись немедленно.
`POST /api/auth/logout` отключает активный socket и удаляет token; состояние
персонажа сервер сохраняет сам в обработчике disconnect.

## Восстановление пароля

1. `POST /api/auth/password-reset/request` принимает email.
2. Сервер всегда возвращает нейтральное сообщение, чтобы не раскрывать наличие
   аккаунта.
3. Для существующего пользователя создаётся случайный token; в `users.json`
   сохраняется только SHA-256 hash и срок действия.
4. Письмо уходит через Nodemailer/SMTP и содержит ссылку
   `PUBLIC_GAME_URL?resetToken=…&login=…`. Unity-клиент ссылку не разбирает:
   логин и код из неё вводятся на экране восстановления.
5. `POST /api/auth/password-reset/confirm` проверяет login, token и новый
   пароль в constant-time сравнении.
6. После успешной смены пароля все сессии аккаунта удаляются.

Переменные production-окружения:

```text
PUBLIC_GAME_URL=https://rangir.ru
SMTP_URL=smtps://user:url_encoded_password@smtp.example.com:465
MAIL_FROM=Кромка <noreply@example.com>
PASSWORD_RESET_TTL_MS=3600000
```

TTL по умолчанию — 60 минут, минимальное значение — 5 минут. Text- и
HTML-версии письма показывают фактический срок из `PASSWORD_RESET_TTL_MS`; при
некорректном значении используется TTL по умолчанию. Если SMTP не настроен или
отправка завершилась ошибкой, временный reset token удаляется, а API отвечает
`503`.

## Персонажи

Персонажи хранятся в `DATA_DIR/saves.json` по `userId`, затем по
`characterId`. API:

| Метод и путь | Назначение |
|---|---|
| `GET /api/characters` | краткий список персонажей аккаунта |
| `GET /api/characters/:id` | метаданные и полное состояние персонажа |
| `POST /api/characters/:id/save` | синхронизация существующего персонажа |
| `DELETE /api/characters/:id` | необратимое удаление отключённого персонажа |

Новый персонаж создаётся при первом корректном Socket.IO `join`. Клиентский
экран требует распределить семь целочисленных характеристик от 1 до 10 с
суммой ровно 40. Сервер отклоняет неверный бюджет целиком и ничего не исправляет
молча. Отдельная обязательная проверка создания требует минимум один и максимум
два профильных навыка и минимум одну и максимум две стартовые черты, а также
пол `female`/`male` и телосложение `slim`/`medium`/`large`, одно из четырёх лиц
своего пола, одну из восьми причёсок и один из восьми цветов волос
`hair_01`–`hair_08`. Невалидный выбор не создаёт запись в `saves.json`.

Канонические варианты и быстрый старт берутся из версионного каталога
`data/kromka/character-progression.json` (клиент читает его через
`GET /api/kromka/character-progression`). Имена пресетов `quick`,
`quickStart`, `mercenary` и `legacyQuickStart` разрешаются только как alias
профиля `independentMercenary` с тем же бюджетом 40; сервер и Unity не содержат
независимых списков характеристик, навыков или перков.

Любой новый персонаж начинает в `tutorialCaravanYard` с пустым инвентарём:
снаряжение и припасы он получает в ходе
[практического обучения](PRACTICAL_TUTORIAL.md). Пропустить обучение можно
только после того, как оно однажды пройдено на аккаунте
(`kromkaTutorialCompletedAt` в `users.json`).

Нормализованная внешность хранится в
`characterProfile.appearance` со схемой `realm.character-appearance.v1`.
Сервер сохраняет первоначальный выбор, включает его в список персонажей и
публичное сетевое состояние и не разрешает последующим клиентским сохранениям
менять имя, характеристики, черты, профильные навыки и внешность. Отсутствующее
или недопустимое поле внешности заменяется вариантом `male + medium + male_01 +
short_crop + hair_03`.

`characterId` уникален во всём сервере, а не только внутри одного аккаунта.
Если клиент предлагает ID, уже принадлежащий другому аккаунту, сервер выдаёт
новый и возвращает его согласованно в `join.characterId` и
`join.self.characterId`. При старте, до открытия порта, сервер проверяет ту же
уникальность во всём `saves.json`: при совпадении первый владелец в
детерминированном порядке сохраняет ID, остальные строки получают новые ID в
profile, summary и ключе store, а social-ссылки на совпавший ID удаляются. До
сверки членства в отрядах симуляции перенос хранится в
`characterIdMigrationJournal`, поэтому сбой между записями продолжит операцию
при следующем старте; связанные записи мира переносятся только по точной
однозначной паре `userId + old characterId`.

Профильные навыки сохраняются как `taggedSkills`. Они дают +5 процентных
пунктов к базовому значению навыка, но итоговая база ограничена 50%.

Экран выбора запускает вход только из стадии выбора персонажа: после клика
стадия сменяется на `Joining`, и повторный клик второй вход не начинает.

## Lease активного персонажа

Успешный socket `join` ставит lock на `characterId` и возвращает случайный
`characterLeaseId`. Lock держится, пока жив socket.

В пределах одного соединения клиент выполняет `join` single-flight. Повтор на
уже присоединённом socket идемпотентно возвращает текущую lease только при
совпадении аккаунта, token, `deviceId`, персонажа и `clientInstanceId`;
несовпадающая попытка отклоняется без отключения действующего персонажа.
Вход вторым socket отклоняется с кодом `character-busy` (персонаж занят) или
`session-busy` (аккаунт уже в игре); Unity-клиент считает оба отказа
временными и повторяет `join`.

Чтение или синхронизация активного персонажа разрешены только владельцу
актуальной комбинации token, `clientInstanceId` и lease (`409` остальным).
Поэтому второй экземпляр клиента не может перезаписать состояние живой сессии.

После disconnect последняя lease запоминается на `SESSION_LOCK_MS`, чтобы
завершившийся HTTP save от того же экземпляра клиента не конфликтовал с
разрывом socket. Без активной или недавней lease сохранение существующего
персонажа отклоняется.

Состояние активного персонажа сервер записывает сам — при значимых действиях и
при disconnect. HTTP-сохранение объединяется с авторитетным состоянием живого
игрока: инвентарь, экипировка, бой, прогрессия, позиция и идентичность берутся
с сервера. Unity использует `POST /api/characters/:id/save` только для
клиентских полей представления — быстрых слотов, предварительно запросив
актуальный документ через `GET /api/characters/:id`.

Unity-клиент допускает игру только после успешного `join`. Во время входа,
reconnect и после disconnect игровые события не отправляются, а локальная
симуляция не включается; отдельного offline-режима нет.

## Удаление

`DELETE /api/characters/:id` требует тело:

```json
{
  "confirmCharacterId": "точный-id-персонажа"
}
```

Активного персонажа удалить нельзя. Перед удалением сервер убирает социальные
ссылки, членство в мировом отряде, locks и recent leases. Операция необратима;
клиент показывает отдельное подтверждение и блокирует остальные действия до
ответа.

## Runtime-файлы и администрирование

`users.json`, `saves.json`, `wasteland-sim.json` и `danger-ecology.json` не
коммитятся. В production задавайте отдельный `DATA_DIR`, например
`/var/lib/realm-of-ashes/data`.

Email и/или пароль существующего аккаунта можно изменить:

```bash
REALM_NEW_PASSWORD='новый-пароль' npm run admin:account -- \
  --login player --email player@example.com
```

Не передавайте production-пароль прямо в историю shell. Безопасный
интерактивный пример и параметры systemd находятся в
[`docs/CODEX_WORKFLOW.md`](../CODEX_WORKFLOW.md).

## Проверка

`npm run smoke` проверяет гостевой вход, регистрацию, конфликт сессии, lease,
отказ записи несуществующего персонажа, обязательные профильные навыки, черты
и внешность, конфликт ID между аккаунтами, стартовую сверку уникальности
`characterId` и её идемпотентность после перезапуска, повторный вход и полный
lifecycle удаления в изолированном `DATA_DIR`. Узкие проверки:
`check:auth-security`, `check:password-reset` и `check:persistence`.
