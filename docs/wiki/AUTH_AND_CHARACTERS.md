# Аккаунты и персонажи

Аккаунт и персонаж — разные сущности. Аккаунт отвечает за вход и список
персонажей; каждый персонаж имеет собственное серверное состояние и отдельную
блокировку активной игровой сессии.

## Регистрация и вход

Регистрация через `POST /api/auth/register` проверяет:

- логин из 3–32 символов `a-z`, цифр и `._@-`;
- уникальный email длиной не более 254 символов;
- пароль длиной 8–128 символов.

Логин и email нормализуются в lower case. Пароль хранится как
PBKDF2-SHA512 hash: 120 000 итераций, случайная 16-byte salt, 64-byte
результат. Сессионный token создаётся через `crypto.randomBytes(32)`.
Клиент также передаёт сохранённый `deviceId`, но сам endpoint регистрации
сейчас не отклоняет пустое значение.

Auth-endpoints ограничены in-memory rate limit. Значения по умолчанию:
20 попыток на пару `IP + login` за 10 минут. Они настраиваются через
`AUTH_RATE_MAX_ATTEMPTS` и `AUTH_RATE_WINDOW_MS`.

## HTTP-сессия

Клиент передаёт token как `Authorization: Bearer ...` или `X-Auth-Token`.
Дополнительные заголовки:

| Заголовок | Назначение |
|---|---|
| `X-Device-Id` | постоянный id устройства |
| `X-Client-Instance-Id` | уникальный id текущей вкладки |
| `X-Character-Lease-Id` | lease активного персонажа, полученная через Socket.IO `join` |
| `X-Device-Type` | `desktop` или `mobile` |
| `X-Control-Type` | `keyboard_mouse`, `touch` или `gamepad` |

Один и тот же аккаунт нельзя одновременно открыть на разных устройствах.
После исчезновения живого socket блокировка неактивной сессии действует до
`SESSION_LOCK_MS` — по умолчанию 120 секунд. На том же `deviceId` новый вход
заменяет старые токены этого устройства.

`POST /api/auth/heartbeat` обновляет `lastSeenAt`, а
`POST /api/auth/logout` отключает активный socket и удаляет token.

## Восстановление пароля

1. `POST /api/auth/password-reset/request` принимает email.
2. Сервер всегда возвращает нейтральное сообщение, чтобы не раскрывать наличие
   аккаунта.
3. Для существующего пользователя создаётся случайный token; в `users.json`
   сохраняется только SHA-256 hash и срок действия.
4. Ссылка отправляется через Nodemailer/SMTP на `PUBLIC_GAME_URL`.
5. `POST /api/auth/password-reset/confirm` проверяет login, token и новый
   пароль в constant-time сравнении.
6. После успешной смены пароля все сессии аккаунта удаляются.

Переменные production-окружения:

```text
PUBLIC_GAME_URL=https://rangir.ru
SMTP_URL=smtps://user:url_encoded_password@smtp.example.com:465
MAIL_FROM=Realm of Ashes <noreply@example.com>
PASSWORD_RESET_TTL_MS=3600000
```

TTL по умолчанию — 60 минут. Если SMTP не настроен или отправка завершилась
ошибкой, временный reset token удаляется, а API отвечает `503`.

## Персонажи

Персонажи хранятся в `DATA_DIR/saves.json` по `userId`, затем по
`characterId`. Старые общие endpoints `/api/save*` удалены; актуальный API:

| Метод и путь | Назначение |
|---|---|
| `GET /api/characters` | краткий список персонажей аккаунта |
| `GET /api/characters/:id` | метаданные и полное состояние персонажа |
| `POST /api/characters/:id/save` | синхронизация существующего персонажа |
| `DELETE /api/characters/:id` | необратимое удаление отключённого персонажа |

Новый персонаж создаётся при первом корректном Socket.IO `join`. Клиентский
экран требует распределить SPECIAL, а сервер ограничивает каждую характеристику
диапазоном 1–10 и уменьшает сумму выше 40. Отдельная обязательная проверка
создания на сервере требует минимум один и максимум два профильных навыка и
минимум один и максимум два стартовых перка. Невалидный выбор этих списков не
должен создавать запись в `saves.json`.

Профильные навыки сохраняются как `taggedSkills`. Они дают +5 процентных
пунктов к базовому значению навыка, но итоговая база ограничена 50%.

## Lease активного персонажа

Каждая вкладка генерирует новый `clientInstanceId`. Успешный socket `join`
ставит lock на `characterId` и возвращает случайный `characterLeaseId`.

Чтение или синхронизация активного персонажа разрешены только владельцу
актуальной комбинации token, `clientInstanceId` и lease. Поэтому скопированная
или фоновая вкладка не может перезаписать координаты и прогресс живой вкладки.

После disconnect последняя lease ненадолго запоминается, чтобы завершившийся
HTTP save от той же вкладки не конфликтовал с разрывом socket.

## Удаление

`DELETE /api/characters/:id` требует тело:

```json
{
  "confirmCharacterId": "точный-id-персонажа"
}
```

Активного персонажа удалить нельзя. Перед удалением сервер убирает социальные
ссылки, членство в мировом отряде, locks и recent leases. Операция необратима;
клиент показывает отдельное подтверждение и блокирует остальные действия до
ответа.

## Runtime-файлы и администрирование

`users.json`, `saves.json` и `wasteland-sim.json` не коммитятся. В production
задавайте отдельный `DATA_DIR`, например `/var/lib/realm-of-ashes/data`.

Email и/или пароль старого аккаунта можно изменить:

```bash
REALM_NEW_PASSWORD='новый-пароль' npm run admin:account -- \
  --login player --email player@example.com
```

Не передавайте production-пароль прямо в историю shell. Безопасный
интерактивный пример и параметры systemd находятся в
[`docs/CODEX_WORKFLOW.md`](../CODEX_WORKFLOW.md).

## Проверка

`npm run smoke` проверяет регистрацию, конфликт сессии, lease, отказ записи
несуществующего персонажа, обязательные tagged skills/perks, повторный вход и
полный lifecycle удаления в изолированном `DATA_DIR`.
