# Аккаунты и персонажи

Аккаунт и персонаж — разные сущности. Аккаунт отвечает за вход и список
персонажей; каждый персонаж имеет собственное серверное состояние и отдельную
блокировку активной игровой сессии.

## Регистрация и вход

Регистрация через `POST /api/auth/register` проверяет:

- логин из 3–32 символов `a-z`, цифр и `._@-`;
- уникальный email длиной не более 254 символов;
- пароль длиной 8–128 символов.

Логин и email нормализуются в lower case. Пароль хранится как
PBKDF2-SHA512 hash: 120 000 итераций, случайная 16-byte salt, 64-byte
результат. Хеширование выполняется асинхронно в ограниченной очереди, поэтому
один вход не блокирует simulation tick и Socket.IO. По умолчанию одновременно
работают не более четырёх PBKDF2-задач, а вся очередь ограничена 64 запросами;
при переполнении auth endpoint отвечает `503` с `Retry-After`.

Сессионный token создаётся через `crypto.randomBytes(32)`. Клиент также
передаёт сохранённый `deviceId`, но сам endpoint регистрации сейчас не
отклоняет пустое значение.

Auth-endpoints ограничены двумя in-memory бюджетами на десять минут:

- 20 попыток на пару `IP + login/email`;
- 60 попыток со всего IP, поэтому перебор случайных логинов не обходит защиту.

Успешный вход очищает только бюджет конкретного login/email, сохраняя общий
IP-бюджет. Таблица ограничена 10 000 записями и при заполнении fail-closed
отклоняет новые попытки вместо неограниченного роста памяти. Production Nginx
передаёт реальный адрес в `X-Forwarded-For`; сервер доверяет этому заголовку
только если прямое соединение пришло с loopback-прокси.

Настройки:

```text
AUTH_RATE_WINDOW_MS=600000
AUTH_RATE_MAX_ATTEMPTS=20
AUTH_RATE_IP_MAX_ATTEMPTS=60
AUTH_RATE_MAX_BUCKETS=10000
PASSWORD_HASH_CONCURRENCY=4
PASSWORD_HASH_MAX_PENDING=64
```

Клиент, отданный самим игровым сервером, сначала использует API текущего origin,
включая нестандартный `PORT`. Для отдельного локального static-сервера
same-origin `404` или не-JSON ответ разрешает fallback на порт `3000`.
GitHub Pages использует `https://rangir.ru`.

## HTTP-сессия

Клиент передаёт token как `Authorization: Bearer ...` или `X-Auth-Token`.
Дополнительные заголовки:

| Заголовок | Назначение |
|---|---|
| `X-Device-Id` | постоянный id устройства |
| `X-Client-Instance-Id` | уникальный id текущей вкладки |
| `X-Character-Lease-Id` | lease активного персонажа, полученная через Socket.IO `join` |
| `X-Device-Type` | `desktop` или `mobile` |
| `X-Control-Type` | `keyboard_mouse`, `touch` или `gamepad` |

Один и тот же аккаунт нельзя одновременно открыть на разных устройствах.
После исчезновения живого socket блокировка неактивной сессии действует до
`SESSION_LOCK_MS` — по умолчанию 120 секунд. На том же `deviceId` новый вход
заменяет старые токены этого устройства.

`POST /api/auth/heartbeat` обновляет `lastSeenAt`, а
`POST /api/auth/logout` отключает активный socket и удаляет token.
Перед logout клиент дожидается финального сохранения. Если сервер его не
подтвердил, logout отменяется до HTTP-запроса и disconnect, текущая сессия
остаётся открытой, а dirty-состояние можно отправить повторно.

## Восстановление пароля

1. `POST /api/auth/password-reset/request` принимает email.
2. Сервер всегда возвращает нейтральное сообщение, чтобы не раскрывать наличие
   аккаунта.
3. Для существующего пользователя создаётся случайный token; в `users.json`
   сохраняется только SHA-256 hash и срок действия.
4. Ссылка отправляется через Nodemailer/SMTP на `PUBLIC_GAME_URL`.
5. `POST /api/auth/password-reset/confirm` проверяет login, token и новый
   пароль в constant-time сравнении.
6. После успешной смены пароля все сессии аккаунта удаляются.

Переменные production-окружения:

```text
PUBLIC_GAME_URL=https://rangir.ru
SMTP_URL=smtps://user:url_encoded_password@smtp.example.com:465
MAIL_FROM=Realm of Ashes <noreply@example.com>
PASSWORD_RESET_TTL_MS=3600000
```

TTL по умолчанию — 60 минут, минимальное значение — 5 минут. Text- и
HTML-версии письма показывают фактический срок из `PASSWORD_RESET_TTL_MS`; при
некорректном значении используется TTL по умолчанию. Если SMTP не настроен или
отправка завершилась ошибкой, временный reset token удаляется, а API отвечает
`503`.

## Персонажи

Персонажи хранятся в `DATA_DIR/saves.json` по `userId`, затем по
`characterId`. Старые общие endpoints `/api/save*` удалены; актуальный API:

| Метод и путь | Назначение |
|---|---|
| `GET /api/characters` | краткий список персонажей аккаунта |
| `GET /api/characters/:id` | метаданные и полное состояние персонажа |
| `POST /api/characters/:id/save` | синхронизация существующего персонажа |
| `DELETE /api/characters/:id` | необратимое удаление отключённого персонажа |

Новый персонаж создаётся при первом корректном Socket.IO `join`. Клиентский
экран требует распределить SPECIAL, а сервер ограничивает каждую характеристику
диапазоном 1–10 и уменьшает сумму выше 40. Отдельная обязательная проверка
создания на сервере требует минимум один и максимум два профильных навыка и
минимум один и максимум два стартовых перка. Невалидный выбор этих списков не
должен создавать запись в `saves.json`.

`characterId` уникален во всём сервере, а не только внутри одного аккаунта.
Если новый клиент предлагает ID, уже принадлежащий другому аккаунту, сервер
выдаёт новый и возвращает его согласованно в `join.characterId` и
`join.self.characterId`. Клиент атомарно принимает такой remap для текущих
token, вкладки и join-попытки: обновляет waiter, выбранный ID, lease-binding и
save-контекст, не инвалидируя собственный socket. Несогласованные два ID
считаются ошибкой протокола. При старте legacy-дубликаты в
`saves.json` обрабатываются до открытия порта: первый владелец в
детерминированном порядке сохраняет ID, остальные строки получают новые ID с
обновлением profile, summary и ключа store. Результат сразу сохраняется, поэтому
повторный запуск миграцию не повторяет. До синхронного сохранения симуляции
`saves.json` держит `characterIdMigrationJournal`; crash безопасно продолжит
операцию, а не потеряет связь со старым ID. Связанные записи мира переносятся
только по точной однозначной паре `userId + old characterId`; членство без
аккаунта, два одинаковых старых персонажа одного аккаунта, старые
reward/arrival-ID и social-ссылки на совпавший ID удаляются, чтобы оставшийся
владелец не получил чужое членство, награду, дружбу или клан.

Профильные навыки сохраняются как `taggedSkills`. Они дают +5 процентных
пунктов к базовому значению навыка, но итоговая база ограничена 50%.

Экран выбора загружает не более одного персонажа одновременно. Повторный клик
во время запроса не создаёт параллельную загрузку, а контекст выбора включает
эпоху и token: смена сессии делает поздний ответ предыдущего запроса
недействительным.

## Lease активного персонажа

Каждая вкладка генерирует новый `clientInstanceId`. Успешный socket `join`
ставит lock на `characterId` и возвращает случайный `characterLeaseId`.

В пределах одного поколения соединения клиент выполняет `join` single-flight:
все параллельные инициаторы ждут один ack. Повтор на уже присоединённом socket
идемпотентно возвращает текущую lease только при совпадении аккаунта,
персонажа и `clientInstanceId`; несовпадающая попытка отклоняется без отключения
действующего персонажа.

На клиенте состояние `joined` считается действующим только при совпадении
текущих token, `characterId`, `clientInstanceId`, socket id и
`characterLeaseId`. Ожидание join запоминает token/character/client-контекст и
после сигнала успеха ещё раз проверяет полную привязку с lease. Поэтому поздний
ack или reconnect другого персонажа не открывает экран старого выбора.

Чтение или синхронизация активного персонажа разрешены только владельцу
актуальной комбинации token, `clientInstanceId` и lease. Поэтому скопированная
или фоновая вкладка не может перезаписать координаты и прогресс живой вкладки.

HTTP-сохранения сериализуются generation-aware single-flight очередью. Новое
состояние, появившееся во время запроса, сохраняется следующей генерацией;
один запуск выполняет не более двух записей и оставляет непрерывный поток
изменений dirty до следующего autosave-интервала. Dirty-флаг нельзя очистить
ответом более старой. Контекстные проверки token,
`characterId`, `clientInstanceId` и lease отбрасывают поздний completion после
смены сессии. Logout и переключение персонажа сначала требуют подтверждённое
финальное сохранение. Пока снимается финальный snapshot, ввод и новые игровые
действия заморожены; неудача отменяет переход до разрыва текущей сессии.

После успешного серверного save обновление платформенного leaderboard
запускается отдельно как best-effort задача. Перед публикацией она повторно
сверяет save-контекст; недоступный или зависший SDK не меняет результат
сохранения и не задерживает logout, переключение персонажа или generation-
drain.

После disconnect последняя lease ненадолго запоминается, чтобы завершившийся
HTTP save от той же вкладки не конфликтовал с разрывом socket.

При наличии token клиент допускает игру только в режиме `server` после
успешного `join`. Во время входа, reconnect и после disconnect действует
fail-closed режим `blocked`: удерживаемый ввод и старые сетевые сущности
очищаются, а локальная симуляция не включается. Актуальный ответ `401` может
очистить token, но уже открытый серверный персонаж сохраняет sticky-требование
online-сервера и остаётся `blocked`. `offline-local` доступен только миру без
token, server-character и предыдущей online-привязки; штатный logout закрывает
online-мир перед снятием требования.

## Удаление

`DELETE /api/characters/:id` требует тело:

```json
{
  "confirmCharacterId": "точный-id-персонажа"
}
```

Активного персонажа удалить нельзя. Перед удалением сервер убирает социальные
ссылки, членство в мировом отряде, locks и recent leases. Операция необратима;
клиент показывает отдельное подтверждение и блокирует остальные действия до
ответа.

## Runtime-файлы и администрирование

`users.json`, `saves.json` и `wasteland-sim.json` не коммитятся. В production
задавайте отдельный `DATA_DIR`, например `/var/lib/realm-of-ashes/data`.

Email и/или пароль старого аккаунта можно изменить:

```bash
REALM_NEW_PASSWORD='новый-пароль' npm run admin:account -- \
  --login player --email player@example.com
```

Не передавайте production-пароль прямо в историю shell. Безопасный
интерактивный пример и параметры systemd находятся в
[`docs/CODEX_WORKFLOW.md`](../CODEX_WORKFLOW.md).

## Проверка

`npm run smoke` проверяет регистрацию, конфликт сессии, lease, отказ записи
несуществующего персонажа, обязательные tagged skills/perks, конфликт ID между
аккаунтами, startup/restart legacy-миграцию, повторный вход и полный lifecycle
удаления в изолированном `DATA_DIR`.
