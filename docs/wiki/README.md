## Игра — это Unity-клиент и авторитетный сервер

Проект состоит из двух частей:

- **Сервер** — один Node.js-процесс `server.js` с модулями `src/server/`:
  REST, Socket.IO и вся игровая логика. Сервер — единственный источник истины
  для многопользовательского состояния.
- **Клиент** — Unity-проект [`unity-client/`](../../unity-client/README.md)
  (Unity 6000.5.8f1, URP 17.5.0). Для игроков игра поставляется как
  WebGL-сборка с корня сайта; Windows Standalone собирается скриптом
  `unity-client/Tools/build-windows.ps1`.

Unity — **единственный клиент**. Пока WebGL-сборки нет (dev, CI), корень сайта
отдаёт страницу ожидания `public/unity-unavailable.html`.

## Быстрый старт

Требуются Node.js 22 и npm:

```bash
npm ci
npm start
```

Сервер слушает `http://127.0.0.1:3000`. Базовая проверка после запуска —
`GET /health`.

Клиент: открыть `unity-client/` в Unity 6000.5.8f1, сцену
`Assets/Scenes/Wasteland.unity` и нажать Play. Адрес сервера задаётся в поле
`BaseUrl` компонента `RoaGameBootstrap` (по умолчанию тот же
`http://127.0.0.1:3000`; WebGL-сборка берёт адрес страницы). Подробности запуска, сборки и редакторских проверок —
в [`unity-client/README.md`](../../unity-client/README.md) и
[`docs/UNITY_PORT.md`](../UNITY_PORT.md).

## Ключевые инварианты

- `server.js` — единственная production-точка входа и источник истины для
  многопользовательского состояния.
- Аккаунты, персонажи и живая симуляция хранятся в `DATA_DIR`; эти runtime-файлы
  не входят в авторские данные репозитория.
- Авторские локации имеют уникальные `id` и лежат в `data/locations/`. Их нельзя
  заменять сгенерированным состоянием живого мира.
- Канонический регион имеет размер 380 × 300 км: 38 × 30 клеток по 10 км,
  8 макрорегионов, 44 места (4 скрытых) и 7 инфраструктурных линий
  (`data/global-map.json`). Игрок ходит по графу из 197 зон по 20 км
  (`data/kromka/zone-graph.json`), места стоят внутри зон.
- Персонаж остаётся независимым наёмником. Он берёт временные контракты сторон,
  но не вступает в постоянную сюжетную фракцию.
- Постоянных NPC-спутников нет. Совместная вылазка может временно объединить
  только живых игроков; жители личной базы остаются на базе.
- У локаций нет настроенного лимита игроков: обычная локация использует общую
  серверную реальность, а встречи и отдельные точки мира получают собственный
  `roomId`.
- Полный snapshot определяет состав комнаты, а частый volatile `playerState`
  отвечает только за плавность движения удалённых игроков; `enemyFrame` двигает
  только уже известных из `enemySnapshot` акторов.
- Unity-клиент — обычный Socket.IO-клиент того же сервера. `join` обязан
  передавать `enemyFrameVersion: 1`, `seq` в `state` строго растёт, пакеты чужой
  комнаты игнорируются по `roomId`.
- Всё преобразование координат правосторонней системы glTF (в ней лежат
  авторские данные) в левостороннюю систему Unity изолировано в единственном классе
  `unity-client/Assets/Scripts/World/RoaCoords.cs`.
- Боевые ресурсы авторитетны на сервере: сохранённый магазин нельзя заполнить
  клиентским снимком, темп атак ограничен `fireRate`, а действие принимается
  только при наличии полной стоимости в AP.
- Временная привязка к каравану, патрулю или активности существует только
  вместе с принятой работой: `worldTaskAction: accept/cancel` атомарно меняет
  профиль и состав, переживает reconnect и снимается при отмене, завершении
  или смерти.
- Игровая видимость сущностей на клиенте проверяется единственной системой
  fog-of-war (`RoaFogOfWar` + `RoaVisibilityGate`); экранные эффекты вроде
  прозрачности крыш не могут раскрыть то, что закрыл gameplay LOS.

## Как поддерживать wiki

1. Сначала сверять утверждение с production-кодом (`server.js`, `src/server/`,
   `unity-client/Assets/Scripts/`), авторскими JSON или `package.json`.
2. Описывать текущее поведение в тематической странице; историю изменения
   добавлять только в changelog. Патч-заметки и датированные дневники не
   заводить — история живёт в git.
3. После правок сервера запускать узкую проверку `npm run check:*`, перед
   передачей существенного обновления — `npm run check`.
4. После правок Unity-клиента запускать `unity-client/Tools/compile-check.ps1`,
   релевантные пробы меню **Кромка** и **Realm of Ashes** или batch-аудит
   `RoaClientAuditRunner.Run`, а также `npm run check:unity-parity`.
5. Для production-настройки использовать
   [инструкцию по производительности](../PERFORMANCE_DEPLOYMENT.md) и
   [workflow развёртывания](../CODEX_WORKFLOW.md).
