# Серверный runtime и производительность

Эта страница описывает текущие циклы `server.js`, сетевой pacing и cache
policy. Production-параметры можно переопределить через окружение, но значения
по умолчанию должны оставаться безопасными для одного Node.js event loop.

## Основные интервалы

| Контур | По умолчанию | Назначение |
|---|---:|---|
| `TICK_RATE` | 20 Гц | движение игроков и финальный room snapshot pass |
| `WASTELAND_SIM_TICK_MS` | 5000 мс | автономная глобальная симуляция |
| `WASTELAND_SIM_SAVE_INTERVAL_MS` | 15000 мс | минимальный интервал обычной записи sim state |
| `ACTIVE_ROOM_AI_TICK_MS` | 200 мс | целевой шаг NPC AI занятой комнаты |
| `ACTIVE_ROOM_AI_MAX_DT` | 250 мс | ограничение накопленного шага NPC AI |
| `ACTIVE_ROOM_HOUSEKEEPING_MS` | 1000 мс | контейнеры, ground items и respawn ресурсов |
| `EMPTY_ROOM_AI_TICK_MS` | 1000 мс | редкий шаг разрешённой пустой комнаты |
| `EMPTY_ROOM_AI_SETTLE_MS` | 15000 мс | короткое AI-окно после ухода последнего игрока |
| полный `snapshot` игроков | не чаще 250 мс | состав и статус комнаты |
| volatile `playerState` | примерно 28–30 мс при изменении | движение удалённого игрока |

`networkPing` не входит в тяжёлый игровой цикл: событие немедленно отвечает ack
с `clientTime` и `serverTime`.

## Разделение сетевых потоков

Полный `snapshot` не является потоком анимации движения. Он сверяет состав
комнаты и авторитетный статус не чаще четырёх раз в секунду.

`playerState` отправляется только при изменении координат, угла, скорости или
флага `moving`. Событие volatile: промежуточный пакет можно отбросить, если
клиент не успевает его принять. Следующий пакет содержит актуальную позицию,
скорость и sequence.

`enemySnapshot` использует адаптивный порог: 80 мс для активных/движущихся
врагов и 360 мс для спокойной комнаты. Ground-items и containers отправляются
событийно и имеют собственные короткие throttle-окна.

## Боевой hot path и сохранение

Сервер держит AP, магазины известных runtime-экземпляров оружия и резерв
боеприпаса в combat-state. Частый профильный пакет передаёт runtime-id владельца,
но другим игрокам сервер по-прежнему публикует только безопасный базовый id.
Сам профильный пакет не меняет экипировку. Для этого существует
`equipmentAction`: сервер принимает один слот, сверяет точный runtime-id и
монотонную `equipmentRevision`, требует 1 AP и одной транзакцией меняет слот,
bag-only инвентарь, AP и ревизию. Короткий кэш `requestId` делает повтор
идемпотентным; reload и боевые обработчики при несовпадении экипировки возвращают
канонический `self`, а не выполняют скрытую смену оружия.

Для нового уникального `attackToken` обработчик последовательно:

1. восстанавливает AP по серверным часам;
2. проверяет минимальный интервал из `weapon.fireRate` с множителем режима;
3. требует полную стоимость действия, оставляя только малый epsilon для
   погрешности чисел с плавающей точкой;
4. проверяет авторитетный магазин и только после этого списывает ресурсы и
   рассчитывает результат атаки.

Отказ по AP или fire-rate происходит до расхода AP, патрона и прочности. Повтор
уже принятого токена может продолжить одну мультитаргет-атаку без повторного
списания, но новый токен не обходит cadence.

Те же проверки выполняет `combatAttack` для выстрела без выбранной серверной
цели. Визуальный `shoot` остаётся отдельным реле, а расход ресурсов больше не
зависит от того, нашёл ли клиент подходящую цель.

`reloadWeapon` переносит ровно `take` патронов из серверного резерва в магазин:
сумма `loaded + reserveAmmo` от перезарядки не меняется. Выстрел уменьшает её,
а HTTP-сохранение, disconnect и reconnect — нет. При сериализации сервер
проецирует канонический `loaded` в `itemRuntime` соответствующего экземпляра; при
следующем `join` ack возвращает восстановленный сервером `combat`, а не
присланную клиентом runtime-копию.

## Занятые комнаты

Базовый player tick не запускает полный NPC AI каждой комнаты на каждом шаге.
Текущий глобальный бюджет разрешает один active-room AI update за итерацию
основного цикла; отдельная комната должна пройти свой шаг не раньше
`ACTIVE_ROOM_AI_TICK_MS`.

Housekeeping отделён от AI и выполняется не чаще раза в секунду:

- суточный restock контейнеров;
- очистка просроченных ground items;
- respawn ресурсных узлов.

Это разделение защищает обработку input и `networkPing` от синхронных всплесков
AI, сериализации и уборки мира.

## Пустые комнаты

Обычная пустая комната спит. Локальный AI разрешён только если:

- не закончилось settle-окно после ухода последнего игрока;
- в комнате продолжается активный realtime-бой;
- onsite-отряд получил команду на выход и должен завершить локальный переход.

На все пустые комнаты действует общий бюджет одного AI update за итерацию.
Пустой update не создаёт новых NPC (`allowSpawn: false`). Обычная жизнь мира
при этом продолжается в `wasteland-sim.js`, без материализации каждой локальной
комнаты.

## Глобальная симуляция

`createWastelandSimulation()` хранит внутреннее состояние как объект. Горячие
server-paths используют `state()` для точечного чтения и вызывают дорогой
`publicState()` только когда публичный snapshot реально нужен.

Перенос прибывшего каравана создаёт комнату и сериализует публичное состояние
только после обнаружения подходящего живого игрока. Slow global tick
логируется, если занимает больше половины настроенного интервала или 500 мс.

Сохранение sim state coalesced: dirty-state не записывается чаще
`WASTELAND_SIM_SAVE_INTERVAL_MS`, кроме явно принудительных операций.

## Загрузка клиента

`public/js/game.js` выполняет `Promise.all` для collider manifest и 59 JS-частей.
После загрузки:

1. проверяется schema collider-каталога;
2. части объединяются в порядке `GAME_SCRIPT_PARTS`;
3. весь код исполняется в общей области через `new Function`.

Это устраняет последовательную блокирующую загрузку, но сохраняет старый
порядок объявлений клиента.

## Cache policy Node.js

Express выставляет:

- `no-cache` для `/`, `index.html`, `js/game.js` и `css/game.css`;
- `public, max-age=31536000, immutable` для ресурсов с query `?v=...`;
- `public, max-age=86400` для остальных static assets;
- ETag и Last-Modified включены.

Shell-файлы остаются revalidation points, а versioned части, модели и текстуры
могут долго жить в кэше.

## Production Nginx

Рекомендуемая схема:

- `/health`, `/api/` и `/socket.io/` проксируются на `127.0.0.1:3000`;
- `public/` раздаётся Nginx напрямую;
- shell-файлы получают `no-cache`;
- versioned ассеты получают долгий `immutable`;
- WebSocket Upgrade и увеличенный read timeout настроены для Socket.IO.

Готовый snippet:
`deploy/nginx/realm-of-ashes.locations.conf`.
Пошаговая инструкция:
[Быстрая загрузка rangir.ru](../PERFORMANCE_DEPLOYMENT.md).

## Наблюдение

- `GET /health` — версия, uptime и размеры основного runtime.
- `networkPing` — клиентский RTT и server clock.
- warning `Slow wasteland simulation tick` — тяжёлый global tick.
- process logs — ошибки sim, transfer, SMTP и записи.

После сетевых/runtime-правок:

```bash
npm run check:server
npm run check:data
node tools/check-progression-sync.js
npm run check:combat
npm run smoke
npm run check
```

Smoke дополнительно фиксирует архитектурные бюджеты: sleeping empty rooms,
разделение active AI и player tick, ленивое чтение sim state, cache headers и
рабочее Socket.IO-подключение.

`check-combat-runtime.js` закрепляет боевые контракты: два независимых магазина
одинакового оружия после переключения, stale-save и reconnect, сохранение общей
суммы патронов, запрет duplicate-join и дропа заряженного runtime-экземпляра,
режимный fire-rate, целевой и бесцельный `attackToken`, ревизионные и
идемпотентные действия экипировки за 1 AP, запрет переэкипировки через
`state`/бой, атомарный отказ для отсутствующего runtime-id, а также отказ без
расхода ресурсов при слишком ранней атаке или недостатке AP.
