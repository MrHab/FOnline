# Серверный runtime и производительность

Эта страница описывает текущие циклы `server.js`, сетевой pacing и cache
policy. Production-параметры можно переопределить через окружение, но значения
по умолчанию должны оставаться безопасными для одного Node.js event loop.

## Основные интервалы

| Контур | По умолчанию | Назначение |
|---|---:|---|
| `TICK_RATE` | 20 Гц | движение игроков и финальный room snapshot pass |
| `WASTELAND_SIM_TICK_MS` | 5000 мс | автономная глобальная симуляция |
| `WASTELAND_SIM_SAVE_INTERVAL_MS` | 15000 мс | минимальный интервал обычной записи sim state |
| `ACTIVE_ROOM_AI_TICK_MS` | 200 мс | целевой шаг NPC AI занятой комнаты |
| `ACTIVE_ROOM_AI_MAX_DT` | 250 мс | ограничение накопленного шага NPC AI |
| `ACTIVE_ROOM_HOUSEKEEPING_MS` | 1000 мс | контейнеры, ground items и respawn ресурсов |
| `EMPTY_ROOM_AI_TICK_MS` | 1000 мс | редкий шаг разрешённой пустой комнаты |
| `EMPTY_ROOM_AI_SETTLE_MS` | 15000 мс | короткое AI-окно после ухода последнего игрока |
| `LEGACY_INPUT_DEADMAN_MS` | 1250 мс, минимум 500 мс | обнуление застрявших осей совместимого `input` |
| полный volatile `snapshot` игроков | не чаще 1000 мс | состав и статус комнаты |
| volatile `playerState` | не чаще 50 мс при изменении | движение удалённого игрока |

`networkPing` не входит в тяжёлый игровой цикл: событие немедленно отвечает ack
с `clientTime` и `serverTime`.

`LEGACY_INPUT_DEADMAN_MS` можно переопределить через окружение. На каждом
player tick сервер проверяет время последнего совместимого `input` и после
таймаута атомарно обнуляет оси, `moving`, `turning`, `vx` и `vz`. Это серверная
страховка от потерянного события отпускания клавиши или оборванного клиента.

## Разделение сетевых потоков

Полный `snapshot` не является потоком анимации движения. Он сверяет состав
комнаты и авторитетный статус не чаще раза в секунду. Список `publicPlayer`
строится только после проверки throttle, а сам снимок volatile: надёжные
`playerJoined`, `playerLeft`, урон и respawn остаются событийными.

`playerState` отправляется не чаще 20 раз в секунду и только при изменении
координат, угла, скорости или флага `moving`; остановка проходит немедленно.
Событие volatile: промежуточный пакет можно отбросить, если клиент не успевает
его принять. Следующий пакет содержит актуальную позицию, скорость и sequence.
Статические профильные поля в этот hot path не входят.

Частый NPC-поток использует компактный абсолютный `enemyFrame`: 80 мс для
активных/движущихся врагов и 360 мс для спокойной комнаты. Он содержит только
динамические поля и монотонный sequence, поэтому потерянный volatile-кадр не
нужно доигрывать из очереди. Надёжный полный `enemySnapshot` сохраняет
статическую схему, экипировку, торговлю и лут для join и структурной сверки.
Ground-items и containers отправляются событийно и имеют собственные короткие
throttle-окна.

## Вход, reconnect и сверка клиента

В v7.76.5 точный повтор `join` на уже присоединённом socket с теми же user,
token, device, client instance и character считается идемпотентным: сервер
возвращает актуальный ack с `alreadyJoined: true`. Если хотя бы одна часть
identity отличается, сервер отклоняет только новый запрос и сохраняет уже
работающего игрока, комнату, lease и соединение.

Клиент держит один `join` на поколение socket. Параллельные вызовы разделяют
Promise, callback старого поколения не меняет текущее состояние, а таймаут
запускает контролируемый reconnect. Для сессии на глобальной карте допустим
`roomId: ""`: готовность определяется подтверждёнными socket id и join-state.
До успешного ack авторитетная online-игра остаётся в режиме `blocked`.

Обычные `ack.self` и событие `authoritativePlayerState` сверяют состояние без
жёсткого переноса локального игрока. Координаты применяются только в обработчике
явного перехода либо для `reason: "movementCorrection"`, поэтому инвентарный или
боевой ack не сбрасывает текущий путь.

## Боевой hot path и сохранение

Сервер держит AP, магазины известных runtime-экземпляров оружия и резерв
боеприпаса в combat-state. Частый профильный пакет передаёт runtime-id владельца,
но другим игрокам сервер по-прежнему публикует только безопасный базовый id.
Сам профильный пакет не меняет экипировку. Для этого существует
`equipmentAction`: сервер принимает один слот, сверяет точный runtime-id и
монотонную `equipmentRevision`, требует 1 AP и одной транзакцией меняет слот,
bag-only инвентарь, AP и ревизию. Короткий кэш `requestId` делает повтор
идемпотентным; reload и боевые обработчики при несовпадении экипировки возвращают
канонический `self`, а не выполняют скрытую смену оружия.

Для нового уникального `attackToken` обработчик последовательно:

1. восстанавливает AP по серверным часам;
2. проверяет минимальный интервал из `weapon.fireRate` с множителем режима;
3. требует полную стоимость действия, оставляя только малый epsilon для
   погрешности чисел с плавающей точкой;
4. проверяет авторитетный магазин и только после этого списывает ресурсы и
   рассчитывает результат атаки.

Отказ по AP или fire-rate происходит до расхода AP, патрона и прочности. Повтор
уже принятого токена может продолжить одну мультитаргет-атаку без повторного
списания, но новый токен не обходит cadence.

Те же проверки выполняет `combatAttack` для выстрела без выбранной серверной
цели. Визуальный `shoot` остаётся отдельным реле, а расход ресурсов больше не
зависит от того, нашёл ли клиент подходящую цель.

`reloadWeapon` переносит ровно `take` патронов из серверного резерва в магазин:
сумма `loaded + reserveAmmo` от перезарядки не меняется. Выстрел уменьшает её,
а HTTP-сохранение, disconnect и reconnect — нет. При сериализации сервер
проецирует канонический `loaded` в `itemRuntime` соответствующего экземпляра; при
следующем `join` ack возвращает восстановленный сервером `combat`, а не
присланную клиентом runtime-копию.

## Занятые комнаты

Базовый player tick не запускает полный NPC AI каждой комнаты на каждом шаге.
Текущий глобальный бюджет разрешает один active-room AI update за итерацию
основного цикла; отдельная комната должна пройти свой шаг не раньше
`ACTIVE_ROOM_AI_TICK_MS`.

Housekeeping отделён от AI и выполняется не чаще раза в секунду:

- суточный restock контейнеров;
- очистка просроченных ground items;
- respawn ресурсных узлов.

Это разделение защищает обработку input и `networkPing` от синхронных всплесков
AI, сериализации и уборки мира.

Коллизии плотной комнаты используют детерминированный uniform-grid как broad
phase. В начале AI-tick строится снимок с запасом на максимальное перемещение,
а в конце публикуется точный индекс для частых player movement packets. Узкая
проверка геометрии не менялась: spatial query лишь сокращает список кандидатов,
а при ошибке автоматически используется прежний полный scan. Радиусы моделей и
преобразованные collider blockers кэшируются по model/scale/position/yaw.

## Пустые комнаты

Обычная пустая комната спит. Локальный AI разрешён только если:

- не закончилось settle-окно после ухода последнего игрока;
- в комнате продолжается активный realtime-бой;
- onsite-отряд получил команду на выход и должен завершить локальный переход.

На все пустые комнаты действует общий бюджет одного AI update за итерацию.
Пустой update не создаёт новых NPC (`allowSpawn: false`). Обычная жизнь мира
при этом продолжается в `wasteland-sim.js`, без материализации каждой локальной
комнаты.

## Глобальная симуляция

`createWastelandSimulation()` хранит внутреннее состояние как объект. Горячие
server-paths используют `state()` для точечного чтения и вызывают дорогой
`publicState()` только когда публичный snapshot реально нужен.

Профили скорости отрядов вынесены в `wasteland-party-speed.js`, а нормализация
участников, лимиты и сверка membership — в `wasteland-party-membership.js`.
Оба модуля не владеют runtime-состоянием и проверяются отдельно.

В v7.76.6 `publicState()` помечает снимок временем последнего simulation tick
`sampledAt` и текущим `serverNow`. Публичная запись отряда содержит точный
участок infrastructure-маршрута от текущей координаты только на
7,5-секундный горизонт сглаживания: дальнейшие обходы и скрытая геометрия
маршрута наружу не передаются. Клиент сохраняет возраст повторно полученного
снимка, отбрасывает более старую пару `sampledAt/serverNow` и плавно ведёт
маркер между штатными пятисекундными tick; секундный HTTP polling больше не
переякоривает движение. Если новый tick не приходит, экстраполяция ограничена
7,5 секунды. Для чистого legacy-потока без часов она отключается; после первого
timestamped-снимка schema downgrade отклоняется как неупорядочиваемый.

Полный `/api/wasteland` запрашивается активной глобальной картой не чаще одного
раза в 5 секунд. Новый интервал отсчитывается после завершения ответа, поэтому
медленная сеть не создаёт непрерывную очередь больших загрузок. Сервер хранит
готовый сериализованный ответ в коротком process-cache и сбрасывает его после
simulation tick. Production Nginx сжимает `application/json` через gzip.

Координаты движущихся отрядов не входят в сигнатуру тяжёлой 3D-геометрии:
существующие модели перемещаются на месте. Территории пересобираются при смене
владельца или границ, но не из-за небольшого изменения визуальной силы клетки.

Перенос прибывшего каравана создаёт комнату и сериализует публичное состояние
только после обнаружения подходящего живого игрока. Slow global tick
логируется, если занимает больше половины настроенного интервала или 500 мс.

Сохранение sim state coalesced: dirty-state не записывается чаще
`WASTELAND_SIM_SAVE_INTERVAL_MS`, кроме явно принудительных операций.

## Загрузка клиента

`public/js/game.js` выполняет `Promise.all` для collider manifest и 60 JS-частей.
После загрузки:

1. проверяется schema collider-каталога;
2. части объединяются в порядке `GAME_SCRIPT_PARTS`;
3. весь код исполняется в общей области через `new Function`.

Это устраняет последовательную блокирующую загрузку, но сохраняет старый
порядок объявлений клиента.

## Cache policy Node.js

Express выставляет:

- `no-cache` для `/`, `index.html`, `js/game.js` и `css/game.css`;
- `public, max-age=31536000, immutable` для ресурсов с query `?v=...`;
- `public, max-age=86400` для остальных static assets;
- ETag и Last-Modified включены.

Shell-файлы остаются revalidation points, а versioned части, модели и текстуры
могут долго жить в кэше.

## Production Nginx

Рекомендуемая схема:

- `/health`, `/api/` и `/socket.io/` проксируются на `127.0.0.1:3000`;
- `public/` раздаётся Nginx напрямую;
- shell-файлы получают `no-cache`;
- versioned ассеты получают долгий `immutable`;
- WebSocket Upgrade и увеличенный read timeout настроены для Socket.IO.

Готовый snippet:
`deploy/nginx/realm-of-ashes.locations.conf`.
Пошаговая инструкция:
[Быстрая загрузка rangir.ru](../PERFORMANCE_DEPLOYMENT.md).

## Наблюдение

- `GET /health` — версия, uptime и размеры основного runtime.
- `eventLoopLagMs`, `wastelandTickMs` и `wastelandPublicCache` в `/health` —
  задержка Node.js event loop, длительность global tick и эффективность cache.
- `networkPing` — клиентский RTT и server clock.
- warning `Slow wasteland simulation tick` — тяжёлый global tick.
- process logs — ошибки sim, transfer, SMTP и записи.

После сетевых/runtime-правок:

```bash
npm run check:server
npm run check:data
node tools/check-progression-sync.js
npm run check:combat
npm run smoke
npm run check
```

Smoke дополнительно фиксирует архитектурные бюджеты: sleeping empty rooms,
разделение active AI и player tick, ленивое чтение sim state, cache headers и
рабочее Socket.IO-подключение.

`check-npc-schedules.js` создаёт отдельную детерминированную симуляцию из
`data/global-map.json` во временной директории. Проверка не читает runtime
`wasteland-sim.json`, сверяет минимальный охват сгенерированных точек, рабочих
групп и NPC, наличие основных дружественных ролей, серверные schedule-contracts
и клиентские sleep/dialogue-анимации.

`check-combat-runtime.js` закрепляет боевые контракты: два независимых магазина
одинакового оружия после переключения, stale-save и reconnect, сохранение общей
суммы патронов, идемпотентный повтор `join` той же socket-identity и безопасный
отказ несовпадающему повтору без разрушения live-session, запрет дропа
заряженного runtime-экземпляра, режимный fire-rate, целевой и бесцельный
`attackToken`, ревизионные и идемпотентные действия экипировки за 1 AP, запрет
переэкипировки через `state`/бой, атомарный отказ для отсутствующего runtime-id,
а также отказ без расхода ресурсов при слишком ранней атаке или недостатке AP.

`check-client-js.js` исполняет generation-drain сохранений: single-flight,
coalescing новых поколений, максимум две записи при непрерывном producer, dirty
после ошибки, bounded retry и смену полного save-контекста. Там же исполняются
отказ logout/switch после неподтверждённого финального save и блокировка
параллельного выбора персонажей.

`check-client-state-integrity.js` исполняет режимы authority и очистку,
same-room gameplay ack guard, context-aware join-waiters (включая глобальную
карту с пустым `roomId`), сохранение/коррекцию позиции, полный lifecycle-сброс
input и камеры, single-flight join, поздние socket callback/timeout,
управляемый reconnect, однократный клиентский износ инструмента и server
deadman. Ранние action guards дополнительно закреплены source-contract
утверждениями; это не полная эмуляция браузера. Реальный серверный
идемпотентный/конфликтующий повтор `join` и строгий harvest с экипированным
инструментом выполняет `check-combat-runtime.js`.
